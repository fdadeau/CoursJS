Projet fondé en Janvier 2009 par Kevin Dangoor, CommonJS (initialement nommé ServerJS) a pour objectif de spécifier un écosystème pour Javascript en dehors du navigateur.

  • Traitements uniquement côté client
  • Pas de posssibilité d'accès au système de fichiers

 Node.js

Node.js a été écrit par Ryan Dahl en 2009 dans le cadre du projet CommonJS. Volonté initiale : remplacer Apache que Dahl trouvait trop lent. Initialement Node.js s'appuyait :

  • sur le moteur V8 de Chrome
  • une boucle d'événements
  • une API bas niveau pour les entrées/sorties

L'architecture de Node.js est non-bloquante ce qui accélère considérablement les traitements.

Node.js est désormais un environnement open-source côté serveur, gratuit, performant, qui s'exécute sur de nombreuses plateformes et qui utilise Javascript.

Node.js peut être utilisé comme environnement d'exécution de scripts à part entière (à l'instar de Python, Ruby, etc.) mais son usage principal reste le web, offrant la possibilité de définir et paramétrer un serveur web complet.

Il existe deux catégories de dépendances :

  • celles nécessaires à l'exécution de l'application, définies dans l'entrée dependencies (ex. express, moongoose, etc.)

Le fichier package-lock.json

En complément du fichier package.json, un fichier package-lock.json est également créé.

Beaucoup plus volumineux, il contient à la fois les numéros des versions des dépendances installées, mais aussi... de leurs dépendances !

Ces deux fichiers sont nécessaires pour permettre à un développeur de récréer le projet en réinstallant le même arbre de dépendance (commande npm install sans autre argument) ; il est donc crucial de les versionner.

À l'inverse, le dossier node_modules n'a surtout pas à être versionné, puisqu'il peut être recréé à partir des informations contenue dans ces deux fichiers de configuration !

Quelques modules intéressants (pour le web) HTTP - Serveur web Le module http

Le module natif http permet de créer un serveur HTTP, c'est-à-dire un service qui écoute sur un port du serveur, reçoit des requêtes en HTTP et réalise un traitement en réponse.

Le module http fournit une méthode createServer((req,res) => {...}) qui prend en paramètre un écouteur de requête (RequestListener) qui est implémenté par une fonction à deux arguments:

  • req : objet représentant la requête HTTP formulée par le client (objet IncomingMessage) - url demandée, query string, données transmises, etc.
    Voir https://nodejs.org/api/http.html.
  • res : objet représentant la réponse HTTP qui sera envoyée au client (objet ServerResponse) - status (200 OK, 3XX redirection, 401 non authentifié, 403 accès refusé, 404 non trouvé, 5XX erreur serveur), entête HTTP, contenu de la réponse, etc.
    Voir https://nodejs.org/api/http.html

La méthode .listen(port) de l'objet http permet de lancer le serveur qui attendra des requêtes sur le port spécifié.

Le code d'un serveur http avec Node.js est très bas niveau : il faut prévoir une réponse pour chaque requête qui va être adressée.

 Le module fs

Comme son nom l'indique, ce module permet d'accéder au système de fichiers pour :

  • lire, écrire dans des fichiers
  • créer, déplacer, supprimer des fichiers, parcourir des répertoires, etc.

Ce module est indispensable dans l'écriture d'un serveur web, pour "servir" les fichiers demandés par la requête HTTP (les lire sur le disque et aller envoyer au client).

L'accès et la lecture d'un fichier se fait via la fonction readFile(path, options, callback) où :

  • path : le chemin vers le fichier à lire
  • options (facultatif) : objet représentant les options {encoding: "...", flag: "r"}
  • callback : fonction avec deux paramètres function(err,data) désignant l'éventuelle erreur lors de la lecture, et le contenu du fichier.

Le callback est déclenché lors de la fin de l'exécution de la méthode → pas de blocage lors de l'accès aux fichiers.

Plan du chapitre Principes généraux Le module Express

Express est un module Node.js permettant de développer des middlewares avec une infrastructure "minimaliste et flexible".

Au delà des fonctionnalités classiques vues précédemment, Express permet de définir simplement le routage au sein d'une application web, facilitant grandement l'implémentation de serveurs RESTful.

Express s'installe avec le gestionnaire de paquets npm
npm install express

Le module s'importe classiquement dans le script avec (syntaxe ESM)
import express from 'express';

Il ne reste plus qu'à instancier l'application Express
const app = express();
et à la paramétrer avant de l'exécuter pour lancer le serveur web.

La documentation complète d'Express se trouve à l'adresse http://expressjs.com/fr

 Les possibilités d'Express

Express permet d'écrire et de paramétrer des serveurs web de façon simple, mais il faut comprendre sa mécanique.

La méthode listen(port, callback) permet de démarrer le serveur web en lui indiquant d'écouteur sur le port spécifié pour recevoir des requêtes HTTP. La fonction de callback sera exécutée lorsque le serveur aura démarré.

Le code :
app.listen(3000, () => { console.log("Serveur démarré !"); });

permet démarrer un serveur qui sera ensuite accessible en local via l'url : http://localhost:3000

L'objectif final d'un serveur web est de produire des ressources HTML, images, vidéo, données texte ou JSON, etc. qui seront transmises au client qui l'interroge (navigateur ou script) via une requête HTTP. Au passage, le serveur peut réaliser des traitements (ex. analyser les données transmises, vérifier l'authentification du client, valider les données, servir des fichiers statiques, etc.)

Express permet donc de définir :

  • des URL qui servent de point d'entrée sur le serveur, appelées routes, généralement organisées dans un contrôleur qui produiront des réponses HTTP
  • des traitements intermédiaires successifs, appelés middlewares, formant un pipeline.

On obtient ainsi une chaîne de traitements : Requête HTTP → Middleware 1 → Middleware 2 → ... → Contrôleur → Réponse HTTP

 Les routes avec Express Une route Express

Avec Express, le routage se définit par 3 éléments : une méthode, une URL, une fonction de traitement (appelée handler).

app.method(chemin, function(req, res) { ... }) permet de définir une route :

  • method peut être get, post, put, delete (et d'autres encore...)
  • chemin est le chemin que l'on souhaite matcher dans l'application (ex. '/api/liste')
  • req représente la requête HTTP formulée par le client (propriétés : query, body - voir http://expressjs.com/fr/4x/api.html#req)
  • res représente la réponse HTTP à forger pour le client (méthodes utiles : .status(code), .type(type_reponse), .end(texte), .send(données), ou json(données_JSON) - voir http://expressjs.com/fr/4x/api.html#res)

Ecriture d'une route (2/3)

Le deuxième élément d'une route est l'URL, exprimée sous la forme d'une chaîne de caractères, donnant le chemin absolu depuis la racine du serveur.

Par exemple, la route ci-dessous :

app.get("/stations", (req, res) => { ... })

définit un point d'entrée du serveur qu'il est possible d'interroger avec une méthode GET avec l'URL (en local) : http://localhost/stations. En cas de déploiement sur une serveur localhost devra être remplacé par l'IP du serveur, ou son nom de domaine.

Les routes peuvent définir des URL paramétrée, en utilisant la syntaxe :identifiant, par exemple :
app.get("/station/:id", (req,res) => { ... }

La valeur de ce paramètre sera accessible dans un objet req.params utilisable dans la fonction handler.

Par exemple, si on consulte l'URL (en local) http://localhost/station/42, req.params.id aura pour valeur 42.

Les middlewares Plan du chapitre Qu'est-ce qu'un middleware ?

Un middleware est une fonction qui exécute un traitement lors d'une requête HTTP. Il peut :

  • exécuter du code,
  • modifier la requète req,
  • modifier la réponse res,
  • terminer la requête,
  • passer la main au middleware suivant

Requête HTTP → Middleware 1 → Middleware 2 → ... → Contrôleur → Réponse HTTP

Express propose des middlewares intégrés qui réalisent des traitements standard, mais tout l'intérêt est de développer des middleware personnalisés.

Qu'est-ce qu'un middleware ?

Un middleware est tout simplement une fonction function(req, res, next) qui admet trois paramètres obligatoires :

  • req la requête HTTP
  • res la réponse HTTP
  • next le passage au middleware suivant

La méthode app.use(function) permet d'ajouter le middleware dans le pipeline de traitement d'Express.

Fonctionnement d'un middleware

next() est essentiel, car il permet de continuer le traitement.

Sans next(), le code s'arrête à la première fonction et n'envoie pas de réponse !

→ Un middleware doit toujours soit appeler next(), soit renvoyer une réponse !

 Fonctionnement d'un middleware

Chaque requête HTTP traverse généralement plusieurs middlewares :

Requête HTTP → Logger → express.json() → Authentification → Contrôleur → Réponse HTTP

En pratique, chaque middleware a une responsabilité unique.

L'ordre d'enregistrement des middleware avec app.use(...) définit l'ordre des traitements (FIFO).

Les middlewares intégrés

Express propose quelques middleware intégrés qui sont bien utiles.

app.use(express.json()) permet d'analyser automatiquement les données au format JSON qui sont contenues dans req.body pour en faire un objet directement exploitable (toujours dans req.body).

app.use(express.urlencoded()) permet d'analyser automatiquement les données transmises depuis un formulaire (de type cle1=valeur1&cle2=valeur2) pour les convertir en objet. Il est essentiel pour permettre de gérer les données transmises au format application/x-www-form-urlencoded.

app.use(express.static('public')) permet de servir directement des fichiers qui seraient présents dans le répertoire spécifié (ici public) du projet. Il est très utile pour servir des pages statiques ou des ressources (fichiers CSS, audio, vidéo, etc.).

Les deux premiers passent la main au suivant. Le dernier ne le fera que si l'URL de la requête HTTP demande une ressource qui n'existe pas dans le chemin spécifié.

Middleware personnalisés

Les middlewares personnalisés sont les fonctions locales qui sont employées pour des traitements spécifiques à l'application. C'est par exemple le cas de la fonction logger vue précédemment.

Un middleware d'authentification est un autre (bon) exemple de middleware personnalisé. Dans le cas où un utilisateur n'est pas authentifié, le traitement se termine (on ne passera pas au suivant) avec une page ou un message spécifique.

Middleware global vs. local

Les middleware globaux sont ceux enregistrés avec app.use(...). Ils s'appliquent à toutes les requêtes HTTP sans distinction d'URL ou de méthode (GET, POST, etc.).

Les middlewares peuvent aussi être attachés à une route spécifique. Dans ce cas, ils ne s'appliquent que sur celle-ci.

Par exemple :
app.get("/favoris", authenticate, getFavoris);
ne s'appliquera que sur l'URL /favoris, et n'effectuera le traitement final (getFavoris) que si l'authentification (authenticate) a réussi.

On remarque, au passage, que l'on peut associer plusieurs handlers à des routes, qui se comportent comme des middleware locaux, créant un pipeline de traitement spécifique à l'URL considérée.

Routes et middlewares

Déclarer un middleware global (avec app.use) permet de factoriser les traitements en évitant de les dupliquer dans chaque route.

A l'inverse, affecter un middleware à une route permet de limiter la portée de celui-ci.

Il existe également un moyen d'affecter un middleware à un ensemble de routes, en précisant un préfixe d'URL en premier paramètre de app.use.

On peut limiter un middleware à une partie de l'application, par exemple :

app.use("/api", logger)

Ainsi le middleware logger sera appelé pour toutes les URL commençant par /api, par exemple :

  • GET /api,
  • GET /api/ressource,
  • POST /api
  • ...
 Les routeurs

Créer des routes, c'est bien. Les organiser c'est mieux. En particulier quand elles commencent à être un peu nombreuses.

Express donne accès à un objet Router permettant d'agréger des ensembles de routes relatives à un traitement spécifique.

Ces routes peuvent être définies dans un module JS à part (dans un répertoire dédié, par exemple /routes) qui sera importé dans l'application principale.

Les routeurs

La méthode app.use(...) pourra ainsi associer ce routeur à l'application, ou à une sous-partie de l'application, grâce à un préfixe.

En utilisant le préfixe /api, les routes utilisables sont donc GET /api et POST /api/new

 Gestion des erreurs (status 5xx)

Express permet de définir un middleware particulier qui est en charge de gérer les erreurs.

Les middlewares de gestion d'erreurs sont comme les fonctions de middlewares classiques, mais avec un paramètre supplémentaire (au début de la liste) représentant l'erreur qui s'est produite.

Celui-ci est appelé automatiquement en cas d'erreur à l'exécution (quelle qu'elle soit). Ainsi tous les contrôleurs bénéficient d'une gestion d'erreur uniforme.

Gestion des ressources inexistantes (status 404)

Pour gérer l'accès à des ressources inexistantes, on s'appuie sur le fait qu'un middleware

  • s'applique indifféremment de la méthode utilisée (GET, POST, etc.), et
  • a tout à fait le droit de renvoyer une réponse.

Pour capturer et gérer une erreur 404 personnalisée, on ajoute à la fin du pipeline, un middleware qui capture une demande qui n'a pas pu être satisfaite précédemment.

On a coutume de distinguer :

Principes Plan du chapitre Pourquoi une API ?

L'objectif est de séparer le client et le serveur.

Client web --> API REST --> Base de données (HTML,CSS,JS) Node + Express PHP, J2EE

L'API fournit au client des services accessibles via HTTP.

Le client n'a pas besoin de connaître :

  • l'organisation interne du serveur
  • la base de données
  • la logique métier

L'API constitue une interface entre les clients et le serveur.

Il s'agit de la manière moderne de construire des applications web, qui donne une grande liberté sur les technologies utilisées pour réaliser le client ou le serveur.

L'architecture REST

REST (REpresentational State Transfer) est une architecture côté serveur qui s'appuie sur le protocole HTTP, qui a été proposée par Roy Fielding dans sa thèse de doctorat.

Ce style d'architecture se définit suivant 6 concepts-clés :

  • Pas d'états côté serveur : seule la requête du client permet au serveur de calculer le résultat, aucune information d'une requête antérieure n'est nécessaire.
  • Mise en cache : possibilité de mettre en cache les réponses pour éviter de surcharger le réseau avec des échanges superflus.
  • Client-Serveur : indépendance de ces entités ; l'interface utilisateur est séparée de celle du stockage des données et peut évoluer séparément.
  • System de couches : le client communique avec un serveur qui peut lui-même s'appuyer sur un autre serveur.
  • Code à la demande (optionnel) : le serveur peut potentiellement transférer du code exécutable au client pour étendre ses fonctionnalités.
  • Interface uniforme : (1) identification des ressources dans les requêtes, (2) manipulation des ressources en utilisant leur représentation, (3) messages se décrivant eux-mêmes (méta-données), (4) utilisation des hypermédia comme moteur de l'application

Plutôt que de penser en termes de fonctionnalités (opération) :

  • /getStations

on se focalise plutôt sur les ressources, et on combine avec une méthode HTTP pour spécifier l'opération :

  • GET /stations

 Les API RESTful

Les architectures REST peuvent être mise en place pour développer des services web. Ceux-ci seront basées sur HTTP et présenteront les éléments suivants :

  • une URL de base (ex. http://api.monsite.com/)
  • un identificateur de ressource formulé comme un URI (ex. /ressource/item42)
  • l'utilisation de méthodes standard HTTP : GET, POST, PUT, PATCH, DELETE

 Les paramètres des requêtes

Certaines actions vont nécessiter des paramètres supplémentaires qui vont être transmis avec la requête. Ces paramètres servent notamment au filtrage, à la recherche, au tri et à la pagination (ex. nouvelles valeurs d'un élément mis à jour, caractéristiques d'une nouvelle entrée, etc.).

Il est possible de matcher un paramètre dans une route, avec la syntaxe :id dans l'URI de la ressource.

L'ensemble de ces paramètres sont accessibles dans l'objet req.params qui représente la requête.

Il est également possible d'avoir des paramètres dans la querystring de l'URL (?param1=val1&param2=val2 ; ces paramètres sont accessibles via req.query de l'objet représentant la requête.

Le corps de la requête sera porté par l'attribut req.body. Celui-ci ne sera instancié que si des parseurs spécifiques (issu du package express) ont été définis au préalable, comme par exemple :

  • app.use(express.json()) pour parser des données au format JSON, ou
  • app.use(express.urlencoded({ extended: true })) pour parser des données application/x-www-form-urlencoded

 Sécuriser une API REST Plan du chapitre Pourquoi sécuriser une API ?

Une API expose des données et des opérations.

Certaines données sont publiques, d'autres sont privées.

Certaines opérations nécessitent des droits particuliers.

Les clients ne sont pas nécessairement dignes de confiance.

Sans mécanisme de protection particulier, n'importe quel client peut effectuer n'importe quelle opération sur le système via l'API !

Authentification + Autorisation

Certaines actions ne doivent pas être accessibles à n'importe quel utilisateur, mais doivent plutôt être réalisables par des utilisateurs connus du système.
On parle alors de mécanisme d'authentification.

Parmi les utilisateurs connus, seuls certains doivent pouvoir effectuer des actions spécifiques (ex. suppression d'un enregistrement par une administrateur).
On parle de rôle d'un utilisateur authentifié.

Inscription et mot de passe

L'authentification classique se pratique à l'aide d'un couple login/password connu de l'utilisateur et du système.

Règle d'or : ne jamais stocker les mots de passe en clair, où que ce soit (fichier, BD, mémoire, etc.)

Différents algorithmes existent pour rendre le mot de passe inexploitable en cas de fuite de données.

Une solution (parmi d'autres) est d'utiliser l'algorithme bcrypt qui calcule un hash

bcrypt.hash(password, 12) → $2b$12$LQv3c1yqBW8...

Ce hash est à sens unique : il n'est pas possible de retrouver le mot de passe d'origine à partir du hash.

Authentification avec mot de passe

Pour s'authentifier, puisqu'il n'est pas possible de déchiffrer le hash, on compare le hash du mot de passe proposé avec celui que l'on a enregistré pour l'utilisateur.

Autres algorithmes de chiffrement

bcrypt, évoqué ici, n'est pas la seule solution.

Pour stocker des mots de passe, on utilise une fonction de dérivation de clé lente et résistante aux attaques par brute-force.

Identifier le client

Pour savoir si un client est autorisé à accéder à une opération, et s'il a le droit de la réaliser, il est nécessaire de pouvoir l'identifier quand il se connecte à l'API.

Après un login :

POST /api/login { login: "alice", password: ... }

Le serveur doit pouvoir reconnaître Alice au moment des requètes suivantes.

Une solution (naïve) consiste à demander au client de renvoyer son identité à chaque nouvelle requête.
Néamoins, il faut éviter que le client puisse simplement dire :

X-User-Id: 42

car c'est identité peut potentiellement facilement être usurpée.

L'identité du client doit être authentifiée par le serveur ! C'est le but de JWT.

Le principe de JWT

JWT (JSON Web Token) est un mécanisme permettant d'authentifier le client auprès du serveur.

Un jeton (token) est généré par le serveur et envoyé au client au moment de son authentification.

Par la suite, le client devra renvoyer ce jeton à chaque requête, comme preuve signée de son identité. Le serveur pourra vérifier que le jeton est valide et permettre ainsi l'accès aux ressources protégées.

Anatomie d'un JWT

Un JWT est composé de trois partie concaténées par un . : HEADER.PAYLOAD.SIGNATURE

  • L'entête spécifie comment le token est signé.
  • Le payload (en français : charge utile) contient les informations utiles à l'identification du client (les claims).
  • La signature permet de garantir l'intégrité de l'ensemble.

Les deux premières parties sont encodées en Base64URL (donc facilement lisibles/modifiables). C'est la troisième partie, la signature crytographique, qui garantit que les deux premières n'ont pas été modifiées.

eyJhbGciOiJIUzI1NiJ9                            // header
.
eyJzdWIiOiIxMjMiLCJyb2xlIjoiVVNFUiJ9            // payload
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c     // signature Anatomie d'un JWT - les claims

Les claims sont placés dans le payload d'un jeton JWT, sous la forme d'un objet (ensemble de clés-valeurs) encodé en Base64URL.

Plusieurs types de claims sont possibles : enregistrés, publics, privés.

Les claims enregistrés correspondent à des clés prédéfines. Tous sont facultatifs.

  • iss (Issuer) : L'émetteur du jeton (ex : l'adresse du serveur d'authentification)
  • sub (Subject) : Le sujet du jeton, c'est-à-dire l'identifiant unique de l'utilisateur (ex : fdadeau)
  • aud (Audience) : Le destinataire du jeton. L'application qui reçoit le JWT doit vérifier qu'elle correspond à cette valeur pour l'accepter
  • exp (Expiration Time) : La date et l'heure d'expiration du jeton, au format Timestamp Unix (secondes écoulées depuis 1970).
  • nbf (Not Before) : La date à partir de laquelle le jeton devient valide (format Timestamp Unix).
  • iat (Issued At) : La date et l'heure à laquelle le jeton a été créé (format Timestamp Unix)
  • jti (JWT ID) : Un identifiant unique pour le jeton. Il est souvent utilisé pour éviter qu'un même jeton soit réutilisé plusieurs fois (attaques par rejeu).

Exemple : name, email, etc.

Les claims privés correspondent à des champs personnalisés sur mesure pour les besoins spécifiques de l'application.
Exemple : role (ADMIN ou USER), etc.

Création d'un JWT

En Node.js le package jsonwebtoken fournit les primitives nécessaires pour la création et la manipulation de JWT.

La création d'un payload s'appuie sur un secret (une chaine de caractères) qui est propre au serveur et sera utilisé pour signer le token. Ce secret n'a pas vocation à être partagé à l'extérieur (il est généralement stocké dans le .env).

Le détail de l'API des JWT avec le package jsonwebtoken est disponible à l'adresse : https://www.npmjs.com/package/jsonwebtoken

 Deux remarques avant d'aller plus loin sur les JWT

La signature sert à authentifier que le contenu du JWT est bien issu du serveur.

En cas de modification d'un payload (par ex. pour remplacer le role: "USER" par role: "ADMIN"), la signature initiale ne correspondra pas à celle du nouveau payload, et la vérification du jeton échouera.

Etant encodé en Base64URL il peut très bien être décodé, et ses données exposées en cas d'interception.

En conséquence : il est interdit de stocker dans le payload des informations sensibles : mot de passe, secret JWT, données confidentielles de l'utilisateur

JWT garantit l'intégrité et l'authenticité du token, pas la confidentialité de son contenu.

Vérification d'un JWT

Le client envoie (généralement) le JWT dans l'entête de la requête HTTP (champ Bearer). Un middleware d'authentification devra donc vérifier la présence de ce champ, et la validité de son contenu. En cas d'erreur, les status HTTP idoines sont utilisés pour signaler celle-ci.

Vérification d'un JWT : authentification

La méthode verify(token, secret, (err, payload) => {...}) valide à la fois

  • la signature et,
  • l'expiration du token

La raison de l'échec est consignée dans le paramètre err, dans le champ name qui peut valoir "JsonWebTokenError", "TokenExpiredError" ou "NotBeforeError") ; le champ message précise l'erreur.

En pratique, on peut/va améliorer le middleware d'authentification pour distinguer une réponse HTTP status 401 (Unauthorized) pour signaler l'expiration du token.

L'authentification ainsi définie peut ensuite être appliquée aux routes qui nécessitent une protection pour l'accès.

routeur.get("/api/protegee", authenticate, getProtectedData)

Maintenant que l'utilisateur est authentifié, la question se pose de savoir si l'opération qu'il souhaite réaliser correspond bien à ses droits (autorisation).

Vérification d'un JWT : autorisation

Le middleware d'autorisation est en charge de vérifier que le rôle de l'utilisateur correspond aux droits attendus pour l'opération.

On peut ensuite rajouter le middleware d'autorisation : routeur.get("/api/delete/:id", authenticate, verifRole("ADMIN"), deleteData)

 Un serveur stateless

Dans les systèmes de session traditionnels, le client transmet un identifiant de session au serveur (ex. cookie PHPSESSID de PHP).
De son côté, le serveur conserve des informations liées à la session de son côté. Il doit donc retrouver l'état lié à la session du client (cf. $_SESSION).

Avec les JWT, le token transmis contient lui-même les informations nécessaires à son interprétation (id de l'utilisateur, rôle, etc. bref, ce que l'on mettait en session en PHP).

De ce fait, on met en place une architecture dite stateless côté serveur.

Attention, cela ne signifie pas qu'il n'y a pas de données liées au client côté serveur, on peut toujours trouver, par exemple en base de données, les utilisateurs, les rôles associés, etc. (stateless = sans état lié à la session côté serveur)

Durée de vie des JWT

Les jetons d'accès (access tokens) ont vocation à avoir une durée de vie relativement courte (de l'ordre de 15 minutes).

C'est une bonne chose pour la sécurité : en cas de vol du token, sa durée d'utilisation est limitée.

C'est une mauvaise chose pour l'utilisateur : il doit potentiellement se reconnecter toutes les 15 minutes.

Pour pallier ce problème, on utilise un second token, nommé refresh token.

Access token + Refresh token

Un refresh token correspond à un jeton supplémentaire, de durée de vie plus longue, qui est créé en même temps que l'access token, et, lui aussi, transmis au client au moment de son identification.

De durée plus longue (plusieurs jours), le refresh token pourra être utilisé par le client pour renouveler son accès, une fois que son actuel access token aura expiré.

Un point spécial d'API, qui s'occupe du renouvellement (rafraîchissement) des access tokens doit alors exister. Pour demander un nouvel accès, le client transmet alors le refresh token comme preuve de son identité.

L'utilisateur n'a ainsi pas à saisir à nouveau son mot de passe.

Gestion des refresh tokens

Le refresh token utilise généralement un secret qui lui est propre (lui aussi stocké dans le .env du projet).

 Pour résumer, côté serveur

L'access token permet un accès, de courte durée.

Pour éviter de le renouveler constamment, on passe par un second jeton, le refresh token, de durée de vie plus longue. Cela permet au client de re-demander l'accès sans devoir resaisir ses identifiants + mots de passe toutes les 15 minutes.

Du point de vue de la sécurité, en cas de vol d'access token, le risque est limité : au bout de 15 minutes (maximum) le client ne pourra plus accéder. Sans refresh token, il ne pourra pas renouveler son autorisation.

Du point de vue du serveur, tout est carré (ou presque). L'utilisation de JWT laisse au client la charge de conserver les tokens et de les envoyer au serveur.

Mais du coup, côté client, comment tout ceci est-il géré ?

 Utilisation des JWT - côté client

Nous avons vu les mécanismes côté serveur : celui-ci transmet des informations au client (access token), vérifie la présence de token pour certaines routes, etc.

Le client, de son côté, devra être en mesure :

  • de transmettre l'access token à chaque requête nécessitant une authentification
  • de demander le renouvellement d'un access token à l'aide de son refresh token

→ charge donc, au client, de stocker ces tokens... sans risquer de se les faire dérober.

Transmettre les tokens du client au serveur

Après le login, le client possède un access token et un refresh token.

Comme vu précédemment, l'access token a vocation à être transmis via l'entête de la requête HTTP, dans le champ Bearer.

On utilise généralement la commande fetch(url, options), que l'on peut encapsuler dans une fonction dédiée que l'on utilisera systématiquement pour interroger le serveur.

Redemander un nouveau jeton d'accès

Dans le cas où l'access token ne soit plus valide, il faut récupérer la réponse, demander un nouvel access token, et relancer la requête avec celui-ci.

On réutilise la fonction précédente et on capture son retour. La fonction refreshAccessToken envoie une requête à /api/refresh et renvoie le nouvel access token.

Où le client doit-il stocker les tokens ?

Plusieurs emplacements de stockage existent pour les access tokens :

  • En mémoire : Sécurisé. Fonctionne bien si l'application web n'est composée que d'une seule page (SPA). C'est le principe souvent utilisé avec les frameworks type React, Vue, etc. Dans le cas d'un changement/rechargement de page, le refresh token sera utilisé pour regénérer un access token (augmente artificiellement les échanges avec le serveur).
  • Dans le stockage de session/local : permet de conserver le token d'une page à l'autre de l'application, tant que l'on a pas fermé la fenêtre de navigateur/pour une durée illimitée. Néanmoins, en cas d'injection de script (attaque Cross-Site Scripting ou XSS) le code malicieux peut accéder au token. A éviter donc.
  • Dans un cookie : les cookies sont automatiquement retransmis au serveur à chaque requête (entête Cookie de la requête HTTP). Cela évite de devoir gérer manuellement l'envoi du token (changement à prévoir dans les fonctions d'authentification montrées précédemment).

Le refresh token doit être un minimum persistant. C'est un élément critique, puisqu'il permet de récupérer de nouveaux accès à l'application, et sur une durée plus longue. Il faut donc éviter qu'il ne puisse être récupéré par un attaquant.

  • Il est fortement déconseillé de placer le refresh token dans un stockage local ou dans un cookie accessible via JS.
  • L'état actuel des pratiques est de l'enregistrer dans un cookie httpOnly qui n'est transmis qu'à l'URL de refresh (path: /api/refresh). C'est le serveur qui s'occupe de réaliser ceci.
Résumé sur les tokens

Les tokens permettent d'authentifier un utilisateur pour protéger certaines routes du serveur.

Les tokens sont signés, ce qui permet de garantir leur intégrité, mais les données qu'ils transportent ne sont pas confidentielles.

L'access token, de durée de vie relativement courte, permet de retenir un certain nombre d'informations liées au client. Il est signé et ne peut ainsi pas être modifié sans connaître le secret qui a permis sa signature.

Le refresh token permet de générer un nouvel access token sans avoir, pour l'utilisateur, à resaisir ses données d'identification.

Dans les deux cas, il s'agit de données sensibles, auquel le code ne doit pas pouvoir avoir accès.

Validation des données entrantes/sortantes Plan du chapitre Pourquoi valider les données ?

Les données reçues par l'API ne sont pas toujours fiables !

Le client peut envoyer :

  • des données manquantes
  • un mauvais type
  • un format incorrect
  • une valeur hors limite
  • des données trop volumineuses
  • des données incohérentes avec les règles métier

La validation est une charge du serveur.

 Où se trouvent les données à valider ?

Avec Express, les données se trouvent à plusieurs endroits.

Principalement, celles-ci se trouvent dans la requête HTTP, mais plus précisément :

  • dans les paramètres d'URL, par exemple /station/:id (accessible via req.params)
  • dans les paramètres de la requête, par exemple ?q=Gare (accessible via req.query)
  • dans le corps de la requête, par exemple dans un objet JSON (accessible via req.body pré-traité par un middleware approprié)
  • dans les entêtes, par exemple Authorisation (accessible via req.headers)

/GET /station/123?limit=10
req.params.id → "123"
req.query.limit → "10"

Les valeurs reçues sont considérées comme des chaînes de caractères jusqu'à validation/conversion.

Validation syntaxique ≠ validation métier

La validation syntaxique consiste à s'assurer que les données ont la bonne forme :

  • champ présent,
  • type correct (ex. chaine, nombre, etc.),
  • format,
  • valeur dans le bon intervalle,
  • ...

express-validator est particulièrement adapté à ce type de vérification qui peut être effectué assez tôt dans la chaîne de traitement.

La validation métier consiste à vérifier que les données respectent des règles propres à l'application développée (par exemple : le paramètre id représente un enregistrement exitant dans la base de données, on ne peut pas ajouter un favori qui existe déjà, etc.).

Requête HTTP → Express → Parsing JSON → Validation syntaxique → Authentification → Autorisation → Validation métier → Contrôleur → ...

Validation syntaxique avec express-validator

Ecrire des middleware de vérification syntaxique peut être rapidement fastidieux et très répétitif.

Le package express-validator permet de réaliser simplement la validation syntaxique des données.

Il s'installe classiquement avec npm install express-validator

On commence par importer les fonctions permettant d'appliquer des vérifications sur les différents éléments de la requête :
import {body, query, header, param} from 'express-validator'

Les validateurs portent sur les éléments de la requête HTTP accessible au travers des fonctions éponymes : body(...), param(...), query(...), header(...) qui prennent en paramètre l'identificateur de la donnée.

Il est ensuite possible de leur appliquer des contraintes (qui peuvent s'enchaîner) :
isInt(), isString(), isEmail, isLength({min: 3, max: 10}), notEmpty(), isIn(["ADMIN","USER"]), etc.

Exemple : param("id").notEmpty().isInt()

Les erreurs éventuellement rencontrées sont automatiquement enregistrées dans la requête HTTP (req).

Traitement des erreurs

Les validateurs enregistrant les erreurs dans la requête, il est donc nécessaire ensuite de les consulter avec validationResult(req) et de renvoyer une erreur appropriée (status 400 - Bad Request).

Le traitement des erreurs est généralement placé dans un middleware réutilisable.

Usage : router.post("/favorites", body("stopId").isString().notEmpty(), handleValidationErrors, createFavorite)

 Schémas de validation

Pour rendre plus lisible les routes en évitant de les surcharger avec d'interminables descriptions des opérations de validation, express-validator permet de décrire des schémas de validation.

Un schéma décrit la structure et les contraintes attendues pour une donnée. Il peut être réutilisé entre plusieurs routes.

Le schéma est ensuite utilisé comme un middleware :
router.post("/favorites", favoriteSchema, handleValidationErrors, createFavorite)

Un schéma décrit le contrat des données d'une API : structures + types + contraintes.
Là où OpenAPI/Swagger documente l'API en décrivant le schéma de validation, express-validator permet de le faire respecter à l'exécution.

Valider et transformer les données

En plus de vérifier les données, express-validator permet également de sanitizer (i.e. nettoyer) celles-ci.

De base, express-validator propose un certain nombre de sanitizers :

  • pour convertir dans un certain type : toInt(), toDate(), toFloat(), etc.
  • pour tranformer une chaîne de caractères : trim(), escape(), normalizeEmail()

Les conversions/transformations appliquées sur les données sont persistantes.

Attention : sanitizer les données ne dispense pas de valider !

Plus de détails : https://express-validator.github.io/docs

 Sécuriser les entêtes des réponses HTTP avec Helmet

Une application web communique par HTTP.

Le serveur peut ajouter des en-têtes HTTP de sécurité à ses réponses afin de limiter certaines attaques, ou comportements dangereux, du navigateur.

Content-Security-Policy: ...    // peut empêcher le chargement de ressources externes
X-Content-Type-Options: nosniff   // respecte le type MIME envoyé par le serveur
Referrer-Policy: no-referrer   // permet d'éviter la transmission de l'URL de la page précédente
Strict-Transport-Security: ...   // force l'usage de HTTPS

La gestion manuelle de ces entêtes est relativement fastidieuse. Pour éviter cela, on peut s'appuyer sur un middleware en charge de son paramétrage : Helmet en fait partie.

Utiliser Helmet dans une API

L'utilisation de Helmet est assez simple. Comme tout package, il faut l'installer : npm install helmet

Il est ensuite nécessaire de l'importer et l'appliquer, au plus tôt dans la chaîne de traitements, de façon à sécuriser tous les retours.

Helmet applique une configuration par défaut qui peut être ajustée au moyen d'un objet passé en paramètre.

Limites de Helmet

Helmet est une couche de sécurité, pas une solution complète. Il ne remplace pas :

  • la validation des données
  • l'authentification JWT
  • l'autorisation et la gestion des rôles
  • le contrôle des droits sur les ressources
  • le hachage des mots de passe
  • la protection contre les injections
  • HTTPS
  • une configuration correcte de CORS
  • la gestion des secrets avec .env
 Contrôler l'accès à l'API Plan du chapitre CORS : gérer les accès à l'API

Un navigateur applique la Same-Origin Policy : une page web ne peut pas délibérément effectuer des requêtes vers une autre origine.

Origine = Protocole + Domaine + Port

L'url http://www.umlp.fr et http://api.umlp.fr:3000 n'ont pas la même origine. Si la page hébergée à la première tente un accès à la deuxième, celui-ci va être refusé.

C'est le navigateur qui bloque !

Le serveur distant va traiter la requête, mais s'il ne fournit pas une entête dans sa réponse (header Access-Control-...) qui indique que l'accès était autorisé, alors le navigateur empêche (le code/l'appelant) d'avoir accès à la ressource.

CORS : quand le navigateur bloque-t-il ? Front-end : http://exemple.com
API       : http://exemple.com/api Front-end : http://www.exemple.com
API       : http://api.exemple.com

Le client envoie (entête requête HTTP) : Origin: http://www.exemple.com

Le serveur répond (entête réponse HTTP) : Access-Control-Allow-Origin: http://www.exemple.com

 Front-end : http://www.exemple.com
API       : http://api.exemple.com

Le serveur ne renvoie pas une autorisation CORS correspondante → blocage du navigateur (même si la réponse a bien été reçue !)

 CORS : requêtes simples vs. complexes

Une requête est dite simple si elle respecte notamment :

  • une méthode : GET, HEAD ou POST
  • uniquement certaines entête safelisted, comme Accept, Content-Language, Content-Type, ...
  • pour Content-Type, uniquement : application/x-www-form-urlencoded, multipart/form-data, text/plain.

Si une requête n'est pas simple, elle est considérée comme complexe.

Dans le cas d'une requête complexe, le navigateur va automatiquement effectuer un preflight qui consiste à s'enquérir du contrôle d'accès configuré sur le serveur avant, le cas échéant, de transmettre sa requête si celle-ci est autorisée.

Requête HTTP (preflight) :
OPTIONS /favorites
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

→

Réponse du serveur :
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: authorization, content-type

CORS avec Express

Il peut donc être utile de pouvoir permettre au serveur d'autoriser certaines connexions cross-origin. Le package cors existe pour réaliser ceci.

Son installation est classique : npm install cors

 Paramétrage de CORS

Le paramétrage est donné par un objet passé à la fonction cors({...}). Les clés de l'objet sont les paramètres que la politique de contrôle d'accès définit.

ParamètreDescriptionExemple
origin Origines autorisées "https://app.example.com"
methods Méthodes HTTP autorisées ["GET", "POST", "DELETE"]
allowedHeaders Headers que le client peut envoyer ["Content-Type", "Authorization"]

En production, on limite explicitement les origines autorisées, à moins d'écrire une API ouverte.

Un mot sur les credentials (1/3)

Dans le contexte HTTP/CORS, credentials désigne les informations d'authentification que le navigateur peut joindre automatiquement à une requête.

Les principaux credentials sont :

  • les cookies
  • les certificats TLS client (rare)
  • dans le modèle Fetch, les informations d'authentification HTTP gérées par le navigateur
 Un mot sur les credentials (2/3)

Lors d'une requête vers le même site, avec fetch, le client va automatiquement envoyer les cookies associés au site.

Ce comportement peut être contrôle (toujours côté client) avec l'option credentials.

La commande fetch("...URL à atteindre...", { credentials: ... }) permet de définir dans quels cas les paramètres d'authentification sont transmis :

Valeur de credentialsComportement
"omit"ne pas envoyer les credentials
"same-origin"n'envoyer les credentials que pour les requêtes same-origin
"include"autorise l'envoi des credentials en cross-origin

La valeur par défaut de fetch est "same-origin".

 Un mot sur les credentials (3/3)

Il est fréquent que l'API manipulée ait une origine différente de l'application qui l'utilise.

1. La demande d'un refresh cookie doit s'accompagner, par le client, d'un envoi de credentials "include" dans la commande fetch.

2. Le serveur doit autoriser explicitement les credentials dans sa réponse :

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

Attention, avec credentials: true dans le paramétrage cors, il n'est pas possible utiliser origin: "*" (représentant l'entête Access-Control-Allow-Origin: *) qui permettrait d'ouvrir l'API à n'importe quelle origine (wildcard *). L'origine devrait, dans ce cas, être explicite.

Envoi et traitement des requêtes

L'envoi d'une requête peut se faire avec la méthode query(...).

La méthode query admet deux syntaxes. Les deux premiers paramètres sont la requête SQL et ses éventuels paramètres. Soit conn la connexion précédemment créée ou un pool de connexions :

  • conn.query("SQL", [Params], function(error, results, fields) {...}) permet de gérer l'appel asynchrone avec une fonction de callback qui admet en paramètre l'erreur éventuellement rencontrée, les résultats renvoyés (tableau d'objets), et les champs du résultat (tableau de chaînes).
  • [results, field] = await conn.query("SQL", [Params]) gère l'envoi de requête comme une promesse (à utiliser dans une fonction asynchrone async).
await pool.query(
  "SELECT * FROM stops"
); → [
  [ { id: 1234, name: "Gare Viotte", latitude: 47.246, longitude: 6.023 }, ... ],
  [ "id", "name", "latitude", "longitude" ]
] Envoi et traitement des requêtes

Pour se prémunir des injections SQL, il est recommandé d'utiliser des paramètres plutôt que d'injecter les données venant du client (et d'oublier de les protéger).

Les paramètres seront automatiquement nettoyés/protégés/échappés pour se prémunir d'une attaque par injection SQL.

À éviter :
❌ conn.query(`SELECT * FROM station WHERE id=${req.param.id}`)

À utiliser :
✅ conn.query("SELECT * FROM station WHERE ?", [req.param.id])

La méthode query permet d'utiliser des raccourcis d'objets, très pratiques dans les requêtes SQL de type INSERT ou UPDATE :
conn.query("INSERT INTO station SET ?", [ { id: 42, name: "...", ...} ]);

Les requêtes préparées (prepared statements) de MySQL ont pour intérêt de séparer la structure de la requête des valeurs des paramètres.

Ce mécanisme peut être mis en action via la méthode execute(SQL,params).

Les deux méthodes permettent d'injecter des paramètres dans une requête SQL et de les protéger au passage. Leur différence tient dans le traitement des paramètres en arrière-plan.

Effectuer des transactions

Certaines opérations nécessitent parfois plusieurs requêtes, qui doivent être considérées de façon atomique (i.e., comme une seule opération). Si une des opérations échoue, on ne souhaite pas forcément conserver l'effet des précédentes.

Par exemple : créer un client avec une adresse de livraison (s'il peut en avoir plusieurs) impliquera de créer le client (table CLIENT) puis de créer la première adresse qui lui sera associée (table ADRESSE_CLIENT).

Les transactions encapsulent une suite de requêtes qui sera ensuite validée (COMMIT).

En cas d'erreur à n'importe quelle étape, une restauration de l'état de la base avant le début de la transaction sera effectuée (ROLLBACK).

 Modèles ORM/ODM Plan du chapitre ORM : manipuler la base avec des objets

Un ORM (Object-Relational Mapping) fait le lien entre :

  • les objets Javascript de l'application
  • les tables relationnelles de la base de données

L'objectif est de manipuler les objets et les modèles plutôt que d'écrire directement du SQL.

L'ORM se charge notamment de :

  • construire les requêtes SQL,
  • mapper les résultats vers des objets,
  • gérer les relations entre entités,
  • parfois gérer les migrations, validations, transactions, etc.

Quelques exemple d'ORM pour Node.js : sequelize (https://sequelize.org/), TypeORM (https://typeorm.io/), Prisma, (https://www.prisma.io/), et bien d'autres...

 Comparaison avec drivers et query builder

Un ORM ajoute encore un niveau d'abstraction par rapport aux drivers ou aux query builders.

La bibliothèque React React : construire des interfaces côté client

React (https://react.dev) est une bibliothèque Javascript permettant de construire des interfaces utilisateur (front-end).

  • React a été créé en 2011 par Jordan Walke, ingénieur logiciel chez Facebook (aujourd'hui Meta).
  • Initialement le projet s'appelait FaxJS, il avait pour objectif de gérer les interfaces dynamiques de Facebook, notamment le fil d'actualité.
    Celui-ci s'appuie sur un système de composants HTML que l'on retrouve encore aujourd'hui.
  • Le projet est déployé sur le fil d'actualité de Facebook en 2011, puis adopté pour celui d'Instagram en 2012.
  • Depuis 2013, le projet est publié en licence open source.

L'objectif de React est de résoudre les problèmes de performance liés à la manipulation directe du DOM (Document Object Model), en introduisant le concept de composants réutilisables et un DOM virtuel.

Le principe de composants React

React propose de visualiser l'interface graphique client comme un ensemble de composants potentiellement imbriqués les uns dans les autres, et réutilisables.

Chaque composant est une entité (techniquement, une fonction) qui propose un rendu sous forme d'éléments (sous-arbre) HTML.

Un composant peut avoir un état qui dépend de valeurs de variables locales ou plus globales. Le rendu du composant permet de refléter l'état courant de l'objet.

Lorsque le composant évolue (les valeurs des variables dont il dépend changent), le rendu du composant doit recalculé pour mettre à jour l'affichage.

C'est le genre de principe que l'on applique aux jeux vidéos (cf. TP de Javascript en Web3 au L2/S4). Sauf que... réactualiser un canvas 60 fois/sec n'est pas un souci. Reconstruire un DOM au sein du navigateur est une opération malheureusement bien plus coûteuse...

 Le principe de DOM Virtuel

Dans le paradigme de React, on a : 1 composant → 1 état → 1 portion de DOM (HTML)

La mise à jour de l'état d'un composant implique la réécriture complète du DOM. Cela peut induire des problèmes de performances dans le cas où de grands pans de l'arbre DOM doivent être changés. Pourtant, on a généralement de petits changements dans certains sous-arbres.

React s'appuie sur un DOM virtuel qui est une copie en mémoire (donc légère) de l'arbre DOM réel issu d'une page HTML, et qui va servir à identifier où les modifications dans l'affichage doivent être réalisées.

  1. Quand l'affichage doit être mis à jour, parce que l'état de l'application a changé, au lieu de mettre à jour directement le DOM de la page (traitement lourd), React créé un nouvel arbre de DOM virtuel.
  2. L'étape suivante est de comparer (étape dite de diffing) ce nouvel arbre avec l'arbre actuellement affiché (version actuelle elle aussi en mémoire).
  3. Pour finir, la mise à jour (étape de réconciliation) identifie précisément quels sont les éléments qui ont changé et doivent faire l'objet d'une mise à jour, garantissant un impact minimal (et peu coûteux) sur le DOM réel.

Il est ainsi aisé de répercuter dans l'affichage la modification du compteur (on réaffiche la zone de texte avec la nouvelle valeur) ou de propager au modèle de données la mise à jour dans l'interface du compteur (mise à jour de count).

React facilite notamment :

Les composants React

Une interface React est composée de composants.

Un composant est généralement une fonction Javascript qui retourne une description de l'interface au format JSX.

Pour un composant Hello qui représente un titre, on aura : function Hello() { return <h1>Hello World</h1>; }

Les composants peuvent eux-mêmes être composés d'autres composants. Le composant racine s'appelle App.

Les composants encapsulent une partie de l'interface et de son comportement.

La syntaxe JSX

JSX pour Javascript XML (ou parfois Javascript Syntax Extension) est une extension du langage Javascript créé pour la bibliothèque React.

Ce langage permet d'utiliser des balises HTML/XML à l'intérieur d'un code Javascript.
Tel quel, le navigateur n'est pas capable de l'interpréter, il faudra qu'il soit d'abord transpilé en HTML et Javascript.

La notation {...} au sein des balises permet d'injecter une expression JS dans le code HTML résultant.

JSX n'est pas du HTML, mais c'est un langage permettant de décrire l'interface.

Transmettre des données au composant

Les props permettent à un composant parent de transmettre des données à un composant enfant. On peut les voir comme les paramètres du composant.

Le composant enfant déclare les propriétés attendues dans la signature de la fonction décrivant le composant JSX, sous la forme d'un objet.

Le composant parent définit ces propriétés comme les attributs de l'élément enfant. Les chaînes sont délimitées de ", tous les autres types doivent être entourés de {...}.

Un composant reçoit ses props de son parent. Il ne doit pas les modifier directement.

Ainsi, JSX utilise les mécanismes de Javascript pour contrôler le rendu.

Affichages de listes

React permet également de réaliser des affichages issus d'itérations (généralement sur des collections de données).

Dans ce contexte, on utilise généralement la fonction map pour transformer la liste de valeurs en liste d'éléments HTML (par exemple <li>).

Si la liste est traitée avec la fonction map, chaque élément de liste doit se voir attribuer un attribut key qui permet à React d'identifier l'élément de la liste.
Cela permet au moteur de rendu de déterminer de manière fiable quels éléments ont été ajoutés/modifiés/supprimés lor d'une mise à jour.

Les événements

React permet d'associer aux composants des événements usuels, portés par les éléments HTML générés, et désignés par une terminologie propre à React (mais proche d'attributs HTML) : onClick, onChange, onSubmit, onFocus, etc.

Le code réalisant le traitement peut être soit délégué à une fonction déjà déclarée, soit directement écrit entre {...}. Comme toutes les fonctions liées aux événements HTML, un paramètre représentant l'événement déclenché peut être utilisé.

Modifier l'état du composant avec useState (1/2)

Un composant peut avoir un état local. Pour enregistrer une variable à l'état local du composant, on utilise le hook

const [val, setVal] = useState(init)

où : val représente la valeur de la variable d'état, setVal est une fonction permettant de changer cette valeur, et init est la valeur initiale de cette variable.

  • Au moment du premier rendu du composant, useState stocke la variable et lui attribue sa valeur initiale. Il retourne un tableau contenant deux éléments : la variable et une fonction permettant sa modification (setter).
  • La variable peut être directement lue pour utiliser sa valeur dans le composant.
  • Il faut utiliser le setter pour modifier la valeur de la variable.
  • L'appel au setter déclenche un nouveau rendu du composant. React réexécute la fonction du composant avec la nouvelle valeur d'état et met à jour le DOM en conséquence.

Les hooks

Un hook en React est une fonction Javascript spéciale qui permet d'utiliser les fonctionnalités du noyau de React (comme la gestion de l'état ou le cycle de vie) à l'intérieur de composants fonctionnels, sans avoir à écrire de classes.

C'est le cas de useState qui permet de créer des variables persistantes dans les composants au sein du moteur de React.

Les hooks ont été introduits en React 16.8 (fév. 2019). Avant leur apparition, les composants sous forme de fonctions restaient "simples". Pour introduire un état ou des traitements spécifiques à certains moments du cycle de vie du composant (montage du composant, mise à jour, destruction), il fallait en passer par une classe qui étendait React.Component.

L'arrivée des hooks permet ainsi de simplifier le code en gardant les composants dans des fonctions. L'écriture de classes pour décrire ses composants est désormais une pratique officiellement dépréciée.

La bibliothèque React propose différents hooks prédéfinis, mais il est également possible d'écrire des hooks personnalisés (une fonction utilitaire qui utilise un autre hook).
Tous les hooks doivent être nommés avec le préfixe use, y compris les hooks personnalisés (c'est ce qui permet à React de les reconnaître).

Un autre hook utile : useEffect (1/3)

Le hook useEffect permet d'exécuter du code en réponse à certains changements du composant.

L'usage est le suivant :
useEffect(function,dependancies)
où le première paramètre est une fonction réalisant le traitement souhaité (ex. chargement de données), les dépendances est un tableau de variables.

Un autre hook utile : useEffect (2/3)

Le tableau de dépendances est analysé par le moteur de React après chaque rendu. React compare les valeurs actuelles avec celles du rendu précédent et réexécute l'effet si au moins une dépendance a changé :

  • [] : l'effet est exécuté après le premier rendu uniquement.
  • [value] : l'effet est exécuté après le premier rendu, puis chaque fois que value change (une liste de valeurs est possible).
  • aucune dépendance (le paramètre n'est pas renseigné) : l'effet est exécuté après chaque rendu.

La fonction en premier paramètre de useEffect peut, si nécessaire, retourner une fonction nommée cleanup qui a pour objectif de nettoyer l'environnement. Le cleanup sera appelé par React avant de réexécuter l'effet une fois que les dépendances changent, ainsi qu'au démontage du composant (i.e. à son retrait de l'interface).

Le nettoyage permet notamment :

  • de supprimer un écouteur d'événement
  • d'arrêter un minuteur
  • de fermer une connexion (à une BD)
 Un autre hook utile : useEffect (3/3)

useEffect sert à synchroniser un composant React avec le monde extérieur : API, navigateur, minuteurs, abonnements ou autres systèmes externes. Il permet de

  • synchroniser l'interface avec un système externe, par exemple le titre de l'onglet du navigateur
  • démarrer puis arrêter un minuteur avec setInterval ou setTimeout

Les communications entre client et serveur

Il existe différents protocoles permettant au client (navigateur) d'échanger avec le serveur.

Il s'agit du protocole classique sur lequel le web s'est construit.

Le protocole HTTP est initié par le client qui contacte le serveur, et le serveur lui envoie une réponse. La connexion est coupée à la fin de chaque échange.

Les sockets sont un mécanisme de communication bi-directionnelle client ⇆ serveur.

Une fois la connexion établie, le client ou le serveur peut envoyer un message à l'autre à n'importe quel moment, jusqu'à fermeture de la socket.

Ce type de communication serveur → client (navigateur) permet de transmettre une information même lorsque la page web n'est pas actuellement active.

Ce système s'appuie sur un mécanisme de souscription utilisant une entité tierce (en l'occurrence, le fabriquant du navigateur).

Nous allons voir ces deux derniers mécanismes.

 Notifications Push Les notifications Push

Les notifications push permettent au serveur de faire parvenir une information au navigateur, même lorsque la page web n'est pas actuellement ouverte au premier plan.

L'architecture de ce mécanisme fait apparaître plusieurs entités qui vont interagir les unes avec les autres.

  • Application Web (côté client) : demande l'autorisation et s'abonne aux notifications
  • Service Worker (coté client) : reçoit les événements Push en arrière-plan
  • Serveur applicatif (côté serveur) : déclenche les notifications pour les abonnés
  • Push Service (entité tierce) : enregistre l'abonnement et relaie, par la suite, les messages vers le navigateur

Le Service Worker est un script qui s'exécute en arrière-plan dans le navigateur, indépendamment de la page web, pour intercepter les requêtes réseau, gérer le cache et permettre le fonctionnement hors ligne ou l'envoi de notifications push.

Procédure d'abonnement et de notification Notification Push - le navigateur parle avec son créateur

Le point essentiel de cette architecture est que le serveur applicatif ne contacte jamais directement le navigateur (forcément puisque celui-ci n'est pas forcément actif au moment où la notification doit être envoyée). Il passe par l'infrastructure Push du navigateur.

Ce Service Push (Push Service) n'est pas géré par le propriétaire du site web, mais directement par l'éditeur du navigateur internet utilisé par votre visiteur.

Chaque grand constructeur ou éditeur de navigateur maintient sa propre infrastructure cloud pour acheminer ces messages. L'appareil autorisant les notifications maintient donc une connexion permanente avec le serveur (similaire aux websockets).

  • Google gère le service pour Chrome et les navigateurs basés sur Chromium (Edge, Opera, Brave) via son infrastructure FCM (Firebase Cloud Messaging).
  • Apple gère le service pour Safari (sur macOS et iOS) via son infrastructure APNs (Apple Push Notification service).
  • Mozilla gère le service pour Firefox via sa propre infrastructure de push (Autopush).

Concrètement : chaque constructeur stocke des jetons enregistrant une souscription et désignant : l'appareil + le navigateur + le site web.

Notifications push - le code client (1/3)

Côté client, la première étape est de demander la permission de notifier le client.
Comme pour la géolocalisation, cette autorisation doit être donnée par l'utilisateur.

On utilise pour cela l'API Notification côté client, et la méthode requestPermission(). Trois réponses sont possibles :

  • "granted" signifie qu'elle est autorisée,
  • "denied" signifie qu'elle est refusée,
  • "default" signifie que l'utilisateur n'a pas encore choisi.
Notifications push - le code client (2/3)

Une fois les notifications acceptées par l'utilisateur, l'étape suivante est d'enregistrer le service worker et de lancer la souscription.

La souscription passe par l'objet pushManager natif du ServiceWorkerRegistration renvoyé par la méthode register.

Notification push - le jeton de souscription

L'objet réceptionné au moment de la souscription, de type PushSubscription, est le jeton renvoyé par le service push, qui sera ensuite transmis au serveur applicatif pour permettre son enregistrement en base.

Le jeton décrivant la souscription a la forme suivante :
{
  "endpoint": "https://googleapis.com...",
  "keys": {
    "p256dh": "BKa...cle_publique...",
    "auth": "qXb...cle_secrete..."
  }
} où :

  • endpoint (adresse de livraison) désigne l'URL exacte du serveur cloud (Google, Apple, Mozilla) vers laquelle le serveur applicatif va envoyer sa requête HTTP POST.
  • La clé p256dh (bouclier de chiffrement) est la clé publique de l'appareil de l'utilisateur. Le serveur applicatif en a besoin pour chiffrer le contenu (payload) de la notification (le titre, le texte, l'icône).
  • La clé auth (jeton d'authentification) est une clé secrète partagée qui permet de prouver au navigateur que le message provient bien de la même session d'abonnement et d'éviter les attaques par usurpation.
 Notifications push - le code client (3/3)

Suite à l'enregistrement du service worker dans le navigateur côté client (navigator.serviceWorker.register("sw.js")), plusieurs étapes se réalisent :

  • Le navigateur télécharge le fichier et vérifie qu'il n'y a pas d'erreur de syntaxe et que la connexion est bien en HTTPS (ou en localhost, considéré comme sécurisé).
  • Le navigateur inscrit le script dans son registre interne. Il lui attribue un périmètre (scope).
  • Le service worker s'installe (déclenche l'événement install auquel le service worker peut répondre).
  • Une fois installé, le service worker passe à l'état actif. Il tourne en tâche de fond de manière indépendante.
Notifications push - le code serveur

Pour permettre de s'authentifier auprès du service push centralisé, on utilise des clés VAPID (Voluntary Application Server Identification).

On utilise une paire de clé : clé publique (côté navigateur) et clé privée (côté serveur applicatif, à ne pas exposer - à cacher dans le .env)

La génération d'une paire de clé VAPID peut se faire via le package web-psuh qui sera utilisé par le serveur pour réaliser une notification push, avec la commande (dans le terminal) : npx web-push generate-vapid-keys
